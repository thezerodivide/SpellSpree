1. Where the range is validated, and how a missing PoK range differs from an unrestricted Bazaar visit

Today (facts from the current file): collectSelectedVendors builds one entry per visit with class, tier (the ticked label) and vendorTier (the vendor to use). runShoppingSpree calls runNavAndShop(entry.name), which calls runSpellSpree() with no arguments. runBazaarShop also calls runSpellSpree() with no arguments. So today nothing carries a range, and the two callers cannot be told apart by what they pass.

NEW DETAIL, proposal:
- Parsing and the first validation happen in collectSelectedVendors, where the existing missing-vendor-mapping check already lives. A new pure function parseTierRange(label) returns low and high (whole numbers, low <= high) or nil plus a reason. A label that does not parse (for example "61-" or "abc") logs an ERROR naming the class and tier, the visit is not added to the list, and nothing is navigated to. That is the same place and the same pattern as the missing-mapping WARN (test S6).
- The visit entry then carries range = { low, high, label }. runShoppingSpree passes it down: runNavAndShop(entry.name, entry.range), then runSpellSpree(range).
- A required argument, not a default. runSpellSpree takes one argument that must be either a range table { low, high, label } (PoK) or the explicit value { unrestricted = true } (the Bazaar passes exactly that). If the argument is nil, or a table that is neither, runSpellSpree validates it first, before it reads the vendor list: it logs an ERROR ("no level range was given for this visit -- buying nothing"), sets the state to Stopped with the reason "No level range", and returns. A caller that forgets to pass the range therefore buys nothing instead of buying everything. A second validation inside runSpellSpree also refuses a range whose low or high is not a whole number or whose low exceeds high (defense in depth against a bad table).
- Tests: a unit test for parseTierRange (the four real labels, and malformed labels); a scenario test with a modified script copy that calls runSpellSpree with no argument (buys nothing, ERROR logged); one with the Bazaar path (buys everything, as today).

2. When skip outcomes are assigned, and what early stops and the skipped counter do

NEW DETAIL, proposal:
- Immediately after the list is built and before the first purchase, one pass classifies every entry. An entry whose level is outside the range, or unreadable, receives its outcome right then: deliberately skipped, with the reason (for example "outside the selected level range 1-25 (Lvl 63)" or "level unreadable (\"--\")"). Entries in range are left with no outcome and go through processEntry exactly as today.
- The main loop skips entries that already have an outcome (a plain check at the top of the loop body, no select, no click, and no 100 ms pause for them, so a vendor with forty out-of-range spells does not add four seconds).
- Early stops: the three stop paths (user Stop, merchant closed, stray cursor item, and processEntry returning stop) call markRemainingNotAttempted, which only sets an outcome on entries that have none (existing code at that function; unit test U10 asserts it keeps entries that already have an outcome and logs no ledger defect). So an out-of-range entry stays "deliberately skipped" and is never relabelled "not attempted because the run stopped". That is also the true statement: it was never going to be attempted at this visit.
- The skipped counter: S.skipped and S.skippedNames are today incremented only in the places where a purchase-time decision skips an affordable-or-not item by name (the unaffordable-quote and out-of-money branches). Entries skipped for another reason (row gone at lookup, for instance) already set an outcome without touching S.skipped. I propose the same for range skips: they are ledger outcomes only, and S.skipped, S.skippedNames, the run-outcome line and the final "Skipped (n)" summary are not changed by them. Reason: those summaries list names, and a 61-70 visit can leave dozens of 1-25 spells; the ledger already counts and names them once, with reasons. The "[list]" line (item E) gives the counts at build time.
- So after any early stop the ledger still adds up: every entry has exactly one outcome (existing test L10 checks that for every scenario, and the new scenarios will be added to it).
