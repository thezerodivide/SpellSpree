A stray item on the cursor stops the run. Range skips and other ledger-only outcomes do not touch `S.skipped`.

## 2. Proposed design items (each is a separate decision)

**A. Data and UI.**
- A table `TOME_VENDORS`: Bard Larquin Julinok; Beastlord Tana Clawguard; Berserker Kurlond Axebringer, then Gaddi Buruca; Monk Beorobin Amondson; Paladin Ulin Velnik; Ranger Keshyk Wardorn; Rogue Blane Darkblade; Shadowknight `Zhao V`karin` (backtick); Warrior Heldin Swordbreaker. Berserker's larger vendor comes first, so the second visit finds nothing new (item E).
- Warrior, Monk, Rogue and Berserker are added to the class list (`CLASS_ORDER`, class-name mapping, detection) with **only** the Discipline Tomes checkbox (they have no spell tiers). Every class that has tome vendors gets a separate checkbox labelled **Discipline Tomes**, next to its range boxes; selecting it needs no range.
- The selection is a new boolean per class. The run's visit list gains one visit per tome vendor of each ticked class, after that class's spell visits. "No vendors selected" and the "Run Shopping Spree (N selected)" count include the tome visits.

**B. Visit kind.** `runSpellSpree` takes a second required argument, the item kind, `'scroll'` (today's behavior, unchanged) or `'tome'`; a missing or unknown kind is refused with an ERROR before anything is read, like the range. A tome visit passes `{ unrestricted = true }` as its range, as the Bazaar does: the Lvl column is read and logged but **never used** (requirement 3). The Bazaar path passes kind `'scroll'` and is unchanged.

**C. Tome identification.** In a tome visit a row is a tome if and only if its name begins exactly with `Tome of ` (case-sensitive, from the start). Everything else is counted as "non-tome, ignored" and never selected or clicked, including `Spell:` and `Song:` scrolls. In a scroll visit tomes stay ignored as today. Evidence: items 3 and 5 of section 1.

**D. Known-discipline check, once per visit, before any purchase.** The known list is read as TAC reads it (point 4 above) and each name is normalized (lower case, every non-alphanumeric character removed). A tome is **known** if its normalized name without `Tome of ` is in that set. A known tome is recorded as "deliberately skipped: discipline already known" at list-build time, never selected or clicked, and not counted in `S.skipped` (ledger-only, as the range skips are). **Tomes whose discipline name cannot be derived** (a tome whose name matches no discipline the character knows or does not know, such as `Diversive Strike`; the build cannot tell these apart from an unknown discipline) are treated like an unknown discipline: they are bought, subject to item E and to the learn-time fallback in item F. If the known list cannot be read (empty scan), the check is off for that visit and the log says so; items E and F still protect.

**E. A run-wide record of tomes already handled.** `S.tomesDone` (cleared at the start of each shopping run, never carried between runs) holds the normalized name of every tome that was bought, learned, or found known or already handled in this run, with the vendor. A tome in that set is recorded as "deliberately skipped: already handled earlier in this run (<vendor>)" and not selected. This is what makes the second Berserker visit harmless, and it protects against a known-list read that is stale or empty. A new run starts fresh (the known check is what protects a re-run).

**F. Buying and learning.** A tome that passes C, D and E goes through the existing purchase steps (exact-name select, verify the selection before Buy, quote and money checks, landing slot, Buy, quantity window, wait for payment), then the **learn step**: right-click the tome where it landed (the same `/itemnotify ... rightmouseup` as a scroll) and check that its slot emptied (the developer's confirmed completion signal), with the same bounded number of attempts. Additionally, a chat event for **"You already know this discipline."** is watched during the learn step: if it fires, the tome is on the cursor and is not consumed. That outcome is recorded as "bought, discipline already known (the check missed it)" with the tome's price; the cursor is cleared with `/autoinventory` and the cursor is read again; if it is still not empty, the run stops with the existing stray-cursor reason. The tome's normalized name is added to `S.tomesDone`. A tome that is neither consumed nor produced the known message after the attempts is "bought, learn not completed", and the run stops, as a scribe failure does today.

**G. Outcomes and labels.** The six outcomes are reused. For tome visits the ledger prints the first two as "bought and learned" and "bought, learn not completed" (a label substitution in the ledger functions, selected by the visit kind; the outcome identities and the counts line format are unchanged); the "already known" cases are reasons under "deliberately skipped", and the slipped-through known tome is under "bought, learn not completed" with the reason above. Requirement 8 (one recorded outcome per tome on the built list, including entries left when a run stops) is satisfied by the existing ledger.

**H. Logging.** Per tome visit: the vendor name read from `Merchant.Name` (logged, not used to gate; the existing target/ID flow still opens the vendor); a `[list]` line with the counts (tomes, non-tome rows ignored, known skipped, handled-earlier skipped, to buy); how the known scan went (count available or not, last filled slot, number known); each known verdict (OBS); each tome's learn result with the chat evidence; the final scan as a count only. Existing spell and song logging is unchanged.

**I. What does not change.** Spell and song purchasing, the level ranges of Step 3, the Bazaar path, the log-follows-the-character behavior, and release `1.6.0`.

**J. Delivery.** SemVer: this adds a feature, so I propose `1.7.0-test.1` (and further `-test.N`), tagged per handoff after the pre-handoff log review (P-1, P-3). Creating `1.7.0` needs the developer's explicit instruction.
